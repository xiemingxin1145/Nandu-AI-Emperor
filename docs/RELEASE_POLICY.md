# 《南渡无悔》Android 更新与签名硬规则

任何 AI、开发者或自动化在制作新的可安装 APK 前都必须先检查本文件。

## 1. 区分开发构建和正式升级交付

- **开发 / PR / 集成 / 真机样板构建**：允许继续使用当前已批准的 `V1.6.1 / versionCode 28`，用于复现、CI、独立地图样板和 STAB-007；必须明确写成“同版本开发测试包”，不得冒充 V1.6.2 正式升级，也不得声称 Android 一定接受覆盖安装。
- **正式升级 / release 分支 / 下一稳定版本**：必须提升 `app/build.gradle.kts` 的 `versionCode`，并同步设置目标 `versionName`。V1.6.2 正式升级至少应满足 `versionCode > 28`；具体值由已批准的 STAB-008 发布任务决定。
- 对玩家可见的版本按 `V1.6.1 -> V1.6.2 -> V1.6.3` 递增；新增明显完整系统才升 `V1.7.0`。不得倒退为 V1.6.0，也不得为每次 CI 运行或内部缺陷修复盲目升级版本。
- Android 安装器可能拒绝降级、不同签名替换或某些同版本覆盖方式；只有 `versionCode` 递增且签名一致的正式包才可宣传为稳定覆盖升级。
- STAB-007 尚未完成、用户尚未批准发布前，不得擅自把当前 28 升到 29 或进入 STAB-008。

## 2. Android “更新”必须保持同一签名

Android 升级安装要求新旧 APK 的 applicationId 和签名证书一致。**签名不能每次换。**

- **V1.6.1 起**，Debug/RC 测试包固定使用 `tools/signing/nandu-dev-debug.keystore`，以 V1.6.1 为长期测试签名基线。
- V1.6.0 RC2 使用的是一次性的手工测试证书，后续复核发现其私钥未保留；因此 RC2 -> V1.6.1 可能需要最后一次卸载重装。V1.6.1 之后禁止再换测试签名。
- 稳定测试证书 SHA-256 指纹：
  `EC:1B:19:D8:FF:E5:19:83:A1:B3:3B:BE:DC:77:24:D9:D4:41:21:8B:7E:DD:6C:6E:20:62:CF:97:D3:84:38:75`
- 该密钥只为公开仓库中的开发测试使用，绝不作为未来 Play Store/生产正式签名。
- 未来正式发行改用私有 release keystore/GitHub Secrets，并从首次正式发行起永久保持同一生产签名。

## 3. Release 分支的 CI 必须拦截旧版本

`release/**` 分支构建前运行 `scripts/check_android_release_policy.sh`。若版本号没有高于 main、稳定测试签名缺失或 Gradle 未引用固定测试签名，构建直接失败，并明确提示先修正版本/签名。

CI 构建后必须再用 `apksigner verify --print-certs` 校验证书指纹；若不是上述固定指纹，APK 不得交付。

## 4. 每次构建或交付 APK 前的检查顺序

1. 先明确交付类型：同版本开发构建，还是已批准的正式升级包；
2. 正式升级才提升 `versionCode` / `versionName`；开发构建保持当前版本并明确标注；
3. 确认签名策略没有变化；
4. 跑项目治理守卫与 unit tests；
5. 构建 APK；
6. 用 `apksigner verify --print-certs` 核对证书；
7. 拆包确认本次新增图片、视频、BGM、旁白、环境声真的进入 APK；
8. 再交给手机安装验收；`DEVICE_REQUIRED` 和 `BLOCKED` 不能因 CI 通过自动变成 `PASS`。

> 重要：以后任何 AI 收到“升级南渡 APK / 打个新包 / 做下一版”的任务，都应先区分“开发测试构建”与“正式升级”。V1.6.1 是固定测试签名基线；真正的正式升级必须提高 versionCode，而所有开发包和正式测试升级包都必须保持同一固定签名。
